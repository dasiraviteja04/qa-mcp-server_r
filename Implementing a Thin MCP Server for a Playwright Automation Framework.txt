Implementing a Thin MCP Server for a Playwright Automation FrameworkObjective of This GuideThis guide explains how to implement a ÒthinÓ MCP server that sits on top of a Playwright automation framework and exposes QA intelligence, not browser control.By the end of this guide, we will have:* A working MCP server* A clean separation between execution and intelligence* A reusable template that can be scaled to any web applicationWhat ÒThin MCP ServerÓ Means (Important)Before writing any code, align on this principle:The MCP server orchestrates and interprets. Playwright executes.This MCP server:* Does NOT control the browser* Does NOT generate selectors* Does NOT replace Playwright MCP* Reads metadata* Triggers test runs* Interprets results* Applies QA rules and policiesStep 0: PrerequisitesEnsure to already have:* A working Playwright framework* Tests tagged with metadata* JSON or machine-readable test reports* Node.js ³ 18 (recommended)Example Playwright command:npx playwright test --reporter=jsonStep 1: Define the Scope of This MCP ServerKeep the first version intentionally small.Minimum Responsibilities (V1)This MCP server should:1. List available tests2. Trigger test execution3. Read last execution results4. Summarize failures5. Expose this via MCP toolsThatÕs it.Avoid feature creep.Step 2: Choose the Technology StackUse boring, stable tech.Recommended Stack (Node.js)* Node.js* TypeScript* Express or Fastify* Official MCP SDK* File-based or lightweight DB storage (JSON / SQLite)Why Node?* Native fit with Playwright* Low friction for QA engineers* Easy CI integrationStep 3: Project Structure (Template)Before implementing the MCP server, we need two clearly separated projects:1. A Playwright automation framework (execution layer)2. A Thin MCP server project (intelligence & orchestration layer)Keeping these separate is critical for scalability and reuse.Step 3.1: Create a Sample Playwright Automation Framework in VS CodeThis section helps you quickly set up a real, working Playwright project that the MCP server can interact with.3.1.1 Choose a Sample Test Automation WebsiteYou can use any stable public demo site. Recommended options:WebsiteWhy itÕs goodhttps://demo.playwright.dev/todomvcOfficial Playwright demohttps://the-internet.herokuapp.comMultiple UI patternshttps://opensource-demo.orangehrmlive.comRealistic login & flowsFor this guide, weÕll assume:https://the-internet.herokuapp.com (You can swap it later without changing MCP logic.)3.1.2 Create the Playwright Project Using VS Code1. Open VS Code2. Open a new terminal3. Create a new folder:4. mkdir playwright-automation5. cd playwright-automation6. Initialize Playwright:7. npm init playwright@latest8. Choose the following options when prompted:o TypeScripto Install Playwright browserso Use GitHub Actions (optional)o Use Playwright TestVS Code will now open a ready-to-use Playwright framework.3.1.3 Recommended Playwright Folder StructureAfter setup, slightly reorganize to make it MCP-friendly:playwright-automation/??? tests/?   ??? smoke/?   ?   ??? login.spec.ts?   ??? regression/?   ?   ??? checkbox.spec.ts??? playwright.config.ts??? package.json??? reports/3.1.4 Add Sample Tests With Metadata (Important)Example 1: Critical Login Testimport { test, expect } from '@playwright/test';test('@critical @smoke Login page loads', async ({ page }) => {  await page.goto('https://the-internet.herokuapp.com/login');  await expect(page.locator('h2')).toHaveText('Login Page');});Example 2: Non-Critical Regression Testtest('@regression Checkboxes can be selected', async ({ page }) => {  await page.goto('https://the-internet.herokuapp.com/checkboxes');  const checkbox = page.locator('input[type="checkbox"]').first();  await checkbox.check();  await expect(checkbox).toBeChecked();});These tags (@critical, @smoke, @regression) are essential for MCP-driven intelligence.3.1.5 Configure JSON Reporting (Mandatory)Update playwright.config.ts:reporter: [['json', { outputFile: 'reports/latest.json' }]],Run tests once to verify:npx playwright testYou should see:reports/latest.jsonThis file is what your MCP server will read.Step 3.2: Create the MCP Server Project in VS CodeNow we create the Thin MCP Server as a separate project.3.2.1 Create a New Project FolderFrom VS Code terminal (outside Playwright project):mkdir qa-mcp-servercd qa-mcp-serverInitialize Node.js:npm init -y3.2.2 Install Required Dependenciesnpm install @modelcontextprotocol/sdk expressnpm install -D typescript ts-node @types/nodeInitialize TypeScript:npx tsc --init3.2.3 MCP Server Folder Structure (Template)Create the following structure manually or via VS Code:qa-mcp-server/??? src/?   ??? server.ts              # MCP bootstrap?   ??? tools/?   ?   ??? listTests.ts?   ?   ??? runTests.ts?   ?   ??? getFailures.ts?   ?   ??? getReleaseRisk.ts?   ??? services/?   ?   ??? playwright.service.ts?   ?   ??? report.service.ts?   ?   ??? policy.service.ts?   ??? config/?   ?   ??? environments.ts?   ?   ??? policies.ts?   ??? types/?       ??? mcp.types.ts??? reports/                   # Copied or mounted Playwright reports??? package.json??? tsconfig.json3.2.4 Link MCP Server to Playwright ProjectYou have two options (choose one):Option A: Shared Reports Folder (Simplest)* Configure Playwright to write reports into:* qa-mcp-server/reports/Option B: Copy Reports After Execution* MCP server triggers Playwright* Copies latest.json into its own reports/ folderOption A is recommended for beginners.3.2.5 Why This Separation MattersPlaywright ProjectMCP Server ProjectExecutes testsDecides what to runKnows selectorsKnows riskKnows DOMKnows historyTool-levelStrategy-levelThis separation makes your automation framework:* Reusable* AI-ready* Enterprise-scalableWhat You Have After Step 3At this point, you have:* A working Playwright automation framework* Tagged, metadata-rich tests* JSON reports for intelligence* A clean MCP server skeleton* Clear separation of responsibilitiesWe are now ready to implement the MCP logic itself, which we cover in the next steps.Step 4: Bootstrap the MCP ServerCreate server.ts.Key Responsibilities* Register MCP tools* Expose them to LLMs* Route requests to servicesConceptual Example (simplified):import { McpServer } from "@modelcontextprotocol/sdk";import { listTests } from "./tools/listTests";import { runTests } from "./tools/runTests";const server = new McpServer({  name: "qa-intelligence-mcp",  version: "1.0.0"});server.tool("list_tests", listTests);server.tool("run_tests", runTests);server.start();At this point:* We have an MCP endpoint* Tools are discoverable by AI agentsStep 5: Implement Tool #1 Ð List TestsPurposeExpose test metadata, not code.InputNoneOutput* Test name* Tags* Feature/module* CriticalityImplementation StrategyDo not parse test files directly if possible. Prefer:* PlaywrightÕs test list output* A pre-generated test catalog JSONExample output structure:[  {    "name": "Checkout Ð UPI payment",    "tags": ["critical", "checkout"],    "feature": "payments"  }]This makes the tool reusable across apps.Step 6: Implement Tool #2 Ð Run TestsPurposeTrigger Playwright safely.Key RuleMCP server invokes Playwright, it does not embed it.Implementation PatternUse child_process to call Playwright CLI:exec(  `npx playwright test --grep @critical --reporter=json`,  callback);Safeguards* Allowlisted commands only* No arbitrary shell access* Environment passed explicitlyStep 7: Capture and Store ReportsAfter execution:* Store JSON reports in /reports* Name by timestamp or build IDExample:reports/??? run-2026-01-27T10-30.jsonThis creates historical intelligence.Step 8: Implement Tool #3 Ð Get FailuresPurposeConvert raw failures into insights.What This Tool Does* Reads latest report* Extracts failed tests* Classifies them (basic logic)Example classification logic:* Failed > 3 times in last 5 runs ? flaky* Only failing in one environment ? env issue* New failure ? regressionEven simple heuristics add value.Step 9: Implement Tool #4 Ð Release Risk AssessmentPurposeAnswer the real question:ÒCan we release?ÓInputs* Build ID or environmentLogic (Example)* Critical test failed ? High risk* Only flaky tests failed ? Low risk* New failures in non-critical flows ? Medium riskOutput{  "risk": "LOW",  "summary": "1 flaky failure, no critical regressions",  "recommendation": "Proceed with deployment"}This is where MCP shines.Step 10: Add Governance & PoliciesCreate policies.ts.Examples:* Self-healing disabled in PROD* Critical failures always block release* AI suggestions are read-onlyThese policies:* Are enforced by MCP* Are invisible to Playwright* Make the system enterprise-safeStep 11: Connect MCP Server to AI AgentsOnce MCP is running:* Any MCP-compatible LLM can query it* Tools are auto-discovered* Responses are structured and safeExample AI question:ÒRun only high-risk tests for checkout and tell me if I can release.ÓThis MCP server:* Selects tests* Runs Playwright* Interprets results* Responds with a decisionStep 12: Make It Reusable Across ApplicationsTo reuse this MCP server:* Replace test catalog source* Update tagging conventions* Adjust policies* Keep MCP logic unchangedThat is the scalability win.Common Mistakes to Avoid* Re-implementing browser control* Parsing DOM inside MCP* Tight coupling to one app* Letting AI write to prod* Overengineering V1Final Mental Model for QA Engineers* Playwright = hands* MCP server = brain* AI agent = voiceEach has a clear responsibility.ConclusionA thin MCP server:* Elevates automation frameworks* Scales QA decision-making* Enables safe AI adoption* Works with any Playwright projectMost importantly:It turns automation output into actionable QA intelligence.
